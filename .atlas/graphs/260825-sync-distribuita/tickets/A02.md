# A02 · Fusione a tre vie per nodo

> Ramo: Fondo condiviso · Tipo: task · Modo: AFK
> Bloccato da: A01
> Stato e dipendenze vivono in `../graph.json`, e si cambiano solo con uno script di mutazione.

## Domanda

Come si fondono due versioni di graph.json ragionando per id di nodo invece che per riga, restando in sola stdlib?
<!-- /atlas:auto -->

## Lavorazione

La base è la nota di A01 (`research/A01-divergenza.md`): gli scenari S1-S9 sono diventati i test di `tests/test_merge.py`.

Alternative scartate:

- **Merge a righe di git**: scartato perché la compattazione degli array su riga unica (`store.py:61`) genera conflitti falsi su lavoro disgiunto (S2b, S5, S6, S9). Il driver parsa i tre JSON e ricostruisce con `store.dumps`: la forma è canonica, l'output deterministico.
- **Marker git nel JSON**: vietati. Un file con `<<<<<<<` non parsa e atlas lo rifiuta come grafo rotto (`store.py:82-83`). Il driver produce sempre JSON valido; su conflitto esce con codice 1 e annota.
- **Conflitti su file separato**: scartato a favore di un campo `conflicts` nel JSON stesso (più stderr), così il segnale sopravvive anche se stderr va perso e A04 lo legge dal grafo.
- **Unione cieca degli array**: scartata. A01 B3 (fog) richiede un set-merge che rispetti le cancellazioni; l'ho generalizzato a tutti gli array (scelta non canonica rispetto a B2, vedi sotto) perché una rimozione fatta da un lato non deve essere resuscitata dal merge.

Scelte non canoniche:

- **Set-merge per tutti gli array, non solo `fog`**: A01 B2 prescriveva l'unione per `blockedBy`/`notes`/`artifacts`/`outOfScope`. Ho applicato la stessa regola del set-merge (un elemento di base sopravvive solo se nessuna parte lo ha tolto, le aggiunte di entrambe entrano): è l'unione nel caso append-only, e in più rispetta le rimozioni. Un `blockedBy` tolto da una macchina e lasciato dall'altra viene tolto, che è la semantica a tre vie.
- **La cancellazione di un nodo non è un gesto del motore**: `add_node` aggiunge, `drop` non esiste. Un nodo assente da una sola parte viene mantenuto (regola "presente solo in una parte → aggiungilo").
- **Rumore locale del claim vince in silenzio**: `pid`, `session`, `at`, `heartbeat`, `fingerprint` (A01 B4) differiscono fra macchine senza essere conflitti; si prende il nostro. `identity` diversa resta un conflitto dichiarato (gara di presa).

File toccati: `payload/core/merge.py` (nuovo), `payload/core/cli.py` (comando `merge-graph`), `payload/core/strings_cli.py` e `payload/core/strings_engine.py` (catalogo it/en), `tests/test_merge.py` (19 test).

## Risposta

**Algoritmo.** Fusione a tre vie per id di nodo, in sola stdlib. I tre grafi si parsano; i nodi si indicizzano per id e si fondono uno a uno; l'ordine finale è canonico (per id), quindi due inserti in coda (S9) non sono più un conflitto.

- Un nodo cambiato da una sola parte → si prende quella; presente solo in una parte → si aggiunge.
- Cambiato da entrambe → confronto campo per campo: array fusi per elemento con set-merge che rispetta le cancellazioni; `owner` rinormalizzato; `meta.updated` = massimo delle date; i campi nuovi scritti da una sola parte (es. `host`/`lease_until` del ramo L) sopravvivono.
- **Chiusura e claim sono blocchi atomici** (`STATO` in `merge.py`): se entrambe le parti chiudono lo stesso nodo con chiusure diverse, o lo prendono con identità diverse, il driver registra una collisione sola e scrive la chiusura/il claim interi di `ours` (mai un miscuglio di campi da due chiusure). Gli altri campi del nodo si fondono comunque.
- Conflitto vero → niente marker git. Il grafo esce comunque JSON valido, con un campo `conflicts: [{"node", "field", "type"}]` dichiarato e la stessa lista su stderr; il driver esce con codice 1.

**Contratto del driver per git** (`atlas merge-graph`):

```
driver = atlas merge-graph %O %A %B
```

Tre path posizionali: `%O` l'antenato comune (può essere `/dev/null` o un file assente, vale come grafo vuoto), `%A` la nostra versione (il driver la riscrive col risultato), `%B` la loro. Uscita 0 = merge pulito, git considera risolto; uscita 1 = conflitto, git registra il file come unmerged e il contenuto scritto è il miglior risultato possibile con `conflicts` annotato.

**Contratto che A03 registra nei progetti ospiti** (perché git usi il driver su graph.json):

- `.gitattributes` (radice della repo):
  ```
  .atlas/graphs/*/graph.json merge=atlas-graph
  ```
- config git (una riga):
  ```
  git config merge.atlas-graph.driver "atlas merge-graph %O %A %B"
  ```

Il nome del driver `atlas-graph` è scelto da A03, ma se lo cambia deve cambiarlo in entrambi i punti. Il path in `.gitattributes` copre tutti i grafi del progetto; se si vuole un solo grafo, il pattern va ristretto allo slug.

### Debito dichiarato

- Il campo `conflicts` scritto nel JSON non viene rimosso dal motore: una volta risolto il conflitto, chi risolve (o A04) deve toglierlo, altrimenti resta una chiave di livello alto che atlas tollera ma che può diventare stantia.
- La cancellazione di un nodo non è un'operazione del motore, quindi il merge la tratta come "nodo presente solo in una parte" e lo mantiene. Se un domani il motore supportasse la rimozione, il driver andrà aggiornato per trattarla come rimozione.
