# L01 · Le ref custom reggono su GitHub?

> Ramo: Lucchetto fra macchine · Tipo: research · Modo: AFK
> Bloccato da: nessuno, prendibile subito
> Stato e dipendenze vivono in `../graph.json`, e si cambiano solo con uno script di mutazione.

## Domanda

GitHub accetta push su refs/atlas/*, e quanto costa in latenza un ls-remote reale? Senza questa risposta il ramo non esiste.
<!-- /atlas:auto -->

## Lavorazione

**Metodo**: fonte primaria = comportamento reale di GitHub, provato sul campo sul remote del progetto (`https://github.com/strawberry-code/atlas.git`, auth gh/GITHUB_TOKEN scope `repo`). 6 misure di latenza di `git ls-remote`, poi ciclo completo crea/verifica/cancella su `refs/atlas/*`, poi test compare-and-swap (due push concorrenti con commit diversi). Completata con la documentazione ufficiale dei limiti di repo. Nessuna traccia lasciata sul remote: ogni ref usa-e-getta è stata cancellata e verificata assente.

**Alternative scartate**: nessuna alternativa al test sul campo, che è la prova dirimente. I docs GitHub non documentano `refs/*` custom, quindi la documentazione è fonte secondaria e il test è la fonte primaria.

**Artefatto**: `research/L01-ref-custom-gh.md` (comandi, output rilevanti, misure, link con data).

## Risposta

**Sì: GitHub accetta push, lettura e cancellazione su `refs/atlas/*`, senza avvisi.** Provato su strawberry-code/atlas il 2026-08-25: `git push origin <commit>:refs/atlas/test-*` → `[new reference]` (rc=0), ref visibile in `ls-remote`, `git push origin :refs/atlas/test-*` → `[deleted]` (rc=0), nessuna traccia residua. Nessun trigger CI né protezione rami: il canale non è un branch, quindi è "pulito" ma anche senza guard-rail.

**Latenza reale di `ls-remote`**: mediana **0.49 s** su 6 prove (0.46-0.50 s a caldo; primo run a freddo 0.72 s), repo con 62 ref, connessione HTTPS da questa macchina. Il costo scala col payload di advertisement (una riga per ref): con pochi lock vivi è trascurabile.

**Proprietà da lucchetto (compare-and-swap)**: il primo push su una ref nuova vince; un secondo push con commit diverso sulla stessa ref è rifiutato (`non-fast-forward`, rc=1). Quindi acquisisci = push, rilascia = delete, e due macchine che contengono lo stesso lock non possono vincerlo entrambe. Attenzione: è la semantica git, non un check dedicato; `--force` (o un fast-forward) sposterebbe la ref, va vietato dal protocollo. La delete è incondizionata: il secondo di due release concorrenti è un errore da trattare come idempotente.

**Avvertenze**:
- Serve auth con scope `repo`; `ls-remote` su repo pubblica non richiede auth.
- Le ref `refs/atlas/*` non appaiono in UI (non sono branch/tag): canale solo-git, invisibile da browser.
- GitHub raccomanda di restare sotto i 5.000 branch per repo ([Repository limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits), letto 2026-08-25): heartbeat persistenti per macchina crescono il conteggio ref col numero di macchine.
- Verifica sul remote di destinazione: repo con policy aziendali, GHES o pre-receive hook potrebbero rifiutare il namespace.

### Debito dichiarato
Prova effettuata su un solo remote (strawberry-code/atlas, repo ordinaria): non copre GHES, policy aziendali, pre-receive hook. La latenza è un ordine di grandezza per questa macchina/connessione, non una costante.
