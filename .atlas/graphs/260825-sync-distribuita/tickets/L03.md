# L03 · Mutex su git refs, fuori dal motore

> Ramo: Lucchetto fra macchine · Tipo: prototype · Modo: AFK
> Bloccato da: L01
> Stato e dipendenze vivono in `../graph.json`, e si cambiano solo con uno script di mutazione.

## Domanda

Prendere, rubare uno scaduto, rilasciare, elencare: reggono come primitive in uno script buttato via, prima di entrare in claims.py?
<!-- /atlas:auto -->

## Lavorazione

Ho costruito un prototipo usa e getta in `scratch/lock-refs/lock.sh` (bash, solo git): implementa su refs git le quattro primitive (acquire, steal, release, list), più `race` per la contesa e `guard` per il varco di corsa. Il bread-and-butter sta in un bare repo locale sotto `scratch/lock-refs/run/`, iterato offline; le stesse primitive girano contro il remote GitHub reale, e le ho validate una volta senza lasciare tracce (ref `l03-validate-*` creata, rubata e cancellata nello stesso ciclo, verifica finale che `ls-remote` non trova nulla).

Iterazione: la prima versione puntava i token a un commit orfano con tree vuoto, e il push falliva con `bad object`. Git non trasporta l'empty tree nel pacchetto, quindi ho dato al commit un tree reale (un blob col payload) e il push ha iniziato a passare. Secondo difetto: lo script faceva `git push` dalla cwd di chi lo lanciava (la repo Atlas), quindi git cercava l'oggetto nel posto sbagliato; ora tutte le git che toccano il remote girano dentro il repo `puppet` che tiene gli oggetti. Terzo: in una race vera il contendente sconfitto viene rifiutato con `reference already exists`, non con `non-fast-forward`; vanno mappati entrambi su "tenuta da altri".

Alternative scartate: la TUI con schermata stabile (il nodo è AFK, non serve interazione), il payload in ISO8601 invece che in epoch (l'epoch si confronta senza parsing), il token come tag annotato invece che come commit (il messaggio del commit si legge con un solo comando).

Artefatto: `scratch/lock-refs/lock.sh`, si guarda con `lock.sh demo` (gira da solo e lascia la sandbox ispezionabile in `scratch/lock-refs/run/`).

## Risposta

Le quattro primitive reggono, sia sul bare repo locale sia contro GitHub reale (validato il 2026-08-25). Le porto in claims.py con i guard sotto.

**Acquire** = push non forzato di un commit il cui messaggio è `ATLAS-LOCK <owner> <expiry-epoch>`. Se la ref non esiste, l'acquire vince; se esiste, git lo rifiuta e la primitiva rilegge la ref e dice chi la tiene. In una race di 5 acquire concorrenti esattamente uno vince: il CAS di git regge, i perdenti vedono `reference already exists` (ref nata durante la loro push) oppure `non-fast-forward` (ref già presente).

**Steal-expired** = rilegge la ref, controlla l'expiry e, se è scaduta, fa push con `--force-with-lease=<ref>:<sha letta>`. Il lease è il compare-and-swap nel varco di corsa: se nel frattempo la ref si è spostata, git rifiuta con `stale info`. Ruba solo la versione che hai letto, mai un'altra.

**Release** = delete con `--force-with-lease`: non cancella una lock che nel frattempo è stata rubata e ri-acquisita. Se la ref è già assente, è idempotente (rc 1, "già libera").

**List** = `ls-remote` di `refs/atlas/*` più fetch in blocco e lettura del messaggio di ogni ref. Mostra possessore, scadenza e stato (ok / EXPIRED / MALFORMED).

Cosa non fanno, e i limiti da tenere a mente:

- Git non controlla il possesso alla delete. Chiunque abbia permesso di push può cancellare qualsiasi ref, anche passando il valore giusto al lease. Il lock è mutua esclusione tra agenti che cooperano, non controllo accessi: il modello di fiducia va dichiarato. La primitiva `release` rifiuta a livello di protocollo (non tua e non scaduta = rc 2), ma non ferma un client buggy o ostile.
- Il ri-acquire dello stesso possessore viene rifiutato: alice che ri-acquista una lock che tiene già riceve `HELD by=alice`. Il commit nuovo non è mai antenato di quello vecchio, quindi git lo tratta come contesa. claims.py deve leggere "tenuta da me" come refresh della scadenza, e "tenuta da altri" come contesa.
- Una lock scaduta si lascia pulire da chiunque (release di un non possessore passa, rc 0): è la pulizia di una lock morta, voluta. Resta distinta dal rilascio di una lock viva altrui, che viene rifiutato.
- Rete assente: il push fallisce con rc non zero e un messaggio chiaro, lo script lo propaga senza traceback. La contesa costa due round trip (push rifiutato, poi rilettura del possessore), da sommare alla latenza misurata in L01 (~0.49 s a ls-remote).

Cosa porto in claims.py: il payload come commit con messaggio e tree reale (mai l'empty tree, non si trasporta); `--force-with-lease` per steal e release; la mappatura di entrambe le rejection su "contesa"; l'expiry in epoch.

Cosa non porto: la logica di possesso dentro git (non esiste, resta nel protocollo); il repo puppet del prototipo (serve solo a creare oggetti locali, il motore creerà i propri); il matching sul testo dell'errore git (è localizzato, va mappato sull'esito).

### Scelte non canoniche

Nessuna: il prototipo sta in `scratch/`, non tocca payload/ né atlascli/, e il nodo non ha imposto un formato di payload.

### Debito dichiarato

Il `--force-with-lease` contro GitHub è provato una volta sola (ref creata, rubata e cancellata in un ciclo). Contro GHES o repo con pre-receive hook il comportamento andrà rivisto sul remote di destinazione. Il costo della contesa (due round trip) è stimato, non misurato contro il remote reale.
